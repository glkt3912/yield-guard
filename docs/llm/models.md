## モデル使い分け

| タスク | モデル | effort | 補足 |
|--------|--------|--------|------|
| 大規模リファクタ・設計判断・長時間の自律実行（例: Issue #811〜#823） | Opus 4.8 | high〜xhigh | 初回ターンに完全なタスク仕様を渡すと真価を発揮 |
| 日常の機能追加・バグ修正・テスト追加 | Sonnet 5 | high | コーディングでほぼ Opus 級。指示を字義通りに解釈する |
| サブエージェントでの探索・分類・単純作業 | Haiku 4.5 | 既定 | 安価・高速。メインループには使わない |

- 迷ったら Sonnet 5。設計判断や広範囲の変更が絡むときだけ Opus 4.8 に上げる
- effort は「高いほど良い」ではない。ルーチンは medium、正確さ最優先のときだけ xhigh/max
- モデル切り替えはプロンプトキャッシュを無効化する。1 セッションはできるだけ 1 モデルで通す

## 現行モデルの行動特性（プロンプトの書き方）

新世代モデル（Opus 4.7 以降 / Sonnet 5）は旧世代と挙動が異なる。以下を踏まえて指示を書く。

- **字義通りに解釈する** — 「全セクションに適用」のようにスコープを明示する。1 例から他へ勝手に一般化しない
- **ツール・スキル・サブエージェントの発動が保守的** — 「〜のときに使う」というトリガー条件を書くと発動率が上がる
- **過剰な step-by-step 指示はかえって品質を下げる** — 手順を列挙するより、ゴールと制約を書く
- **「必ず」「CRITICAL」は過剰発動の原因** — ただし CLAUDE.md の Git / Secrets 安全規則のような絶対ルールは強い表現のままにする

## タスク仕様の渡し方

Opus 4.8 の長時間自律実行は初回ターンの仕様の質に依存する。issue をそのまま渡すときは、
`.github/ISSUE_TEMPLATE/task.md` の「完了条件」欄（検証可能なチェックリスト）を必ず埋める。

## 変更後の検証手順

コードを変更したら次の順で検証する（詳細は各タスクのエントリ doc 参照）。

1. `make test` — `go test -race ./...` + vitest
2. `make lint` — golangci-lint + eslint + tsc --noEmit
3. Go 型を変更した場合のみ `make swagger` → `swagger.json` をコミットに含め、`make swagger-check` でドリフト確認

## サブエージェントの使いどころ

Opus 4.8 は既定ではサブエージェントを使いたがらない。次の場合は明示的に委譲する。

- backend と frontend の独立した変更 → 並列で走らせる
- 複数ファイル・命名規則の横断探索 → ファンアウトさせる
- 単一ファイルの読み取りや逐次的な操作 → 直接行う（委譲しない）
