# ADR — 決定記録

## なぜ設けたか

`docs/architecture.md` の「技術選定の背景（Why）」には、採用した技術の理由が5件書かれている。
一方で `却下` / `代替案` / `採用しない` の記述は同ファイルに1件も無い。

つまり従来の記録は **採用理由だけが溜まり、代替案が明示的に死なない形式**だった。
ADR はこれを補う。効くのは形式ではなく **「却下した案」欄** ただ1つである。

## いつ書くか

`CLAUDE.md` の Conventions を参照。要約すると:

- 既存機能と目的が重複する機能を追加するとき
- ユーザーに見せる指標・入口・既定値を変えるとき
- 「両方用意する」という結論に至ったとき

このリポジトリでは**製品判断も ADR の対象**とする（対象ユーザー・入口・見せる指標など）。
技術判断だけを書く場所ではない。

## 書き方

`_template.md` をコピーし、`YYYYMMDD-<slug>.md` の名前で作る
（例: `20260910-input-mode.md`）。**連番は使わない** — worktree を並走させると採番が衝突するため。

守る点は3つ。

1. **`## 検討した案` を `## 決定` より先に埋める。**
   逆順にすると、結論を書いてから却下理由を後付けすることになり、この文書の意味が無くなる
2. **`## 却下した案` は空欄不可。**
   却下理由は「劣っているから」ではなく「`docs/product-decision.md` の問いに答えないから」で書く
3. **両方残す場合も `## 決定` に1行で書く。**
   専用の節は設けていない。どちらが既定かを書かない限り、それは決定ではなく先送りである

## 前提

ADR には却下の基準が必要である。基準は `docs/product-decision.md`
（対象ユーザー1人・答える問い1つ）が供給する。
**基準が未記入のまま ADR を書くと、結論は「両方採用」に流れる。**

ただし基準が未記入でも ADR を書くこと自体は妨げない。その場合は
「対象ペルソナの問い」に `未決定` と書き、状態を **暫定** とする。
問いが決まった時点で却下理由を書き直す。

## 既存の重複についての注記

`docs/usecases.md` には目的が近い機能が併存する箇所がある
（用途地域リスクの自動検出と手動入力、入力モードの Quick / 詳細など）。
2026-09 時点で調査した限り、これらには**いずれも既定値または役割の区別が実装済み**である。

| 併存 | 既定 / 役割の区別 | 実装箇所 |
|------|------------------|---------|
| 入力モード Quick / 詳細 | 既定 `quick`。詳細は段階開示 | `Dashboard.tsx` の `simulationMode` 初期値 |
| 検討の順序 物件起点 / エリア起点 | 既定 `simulation`。エリア探索は明示選択タブ | `Dashboard.tsx` の `activeTab` 初期値 |
| 利回り `marketGrossYield` / `grossYield` | 判定・見出しは `marketGrossYield`。`grossYield` は二次指標 | `KpiStrip` / `StatusSummary` / `lib/pdf/verdict.ts` |
| 用途地域リスク 自動 / 手動 | 自動はエリア代表値、手動は物件個別（任意入力） | `LandPriceAnalysis` / `sections/PropertyInfoSection.tsx` |

したがって**過去分の ADR バックフィルは行わない**。
記録が無いのは事実だが、決定そのものは実装内に存在する。
ADR は今後の判断に対してのみ適用する。
